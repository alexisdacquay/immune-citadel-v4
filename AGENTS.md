# Immune Citadel v4

A tower-defence game inside the human body, for teens (12-15); education first. The whole game is `index.html` (vanilla JS canvas). The save API lives in `server/`.

- **Docs:** `docs/STATUS.md` (where things stand, what is next: read first), `README.md` (what and how to run), `docs/SPEC.md` (player journeys, acceptance criteria), `docs/TEAM.md` (agent team, the loop, QA in two stages, the test plan), `docs/OPERATIONS.md` (environments, releases, telemetry, alert), `docs/PIPELINE-PLAN.md` (deploy-pipeline steps and proof), `docs/OBSERVABILITY-PLAN.md` (monitoring: Sentry, own gameplay events, Better Stack; steps and proof), `docs/EVENTS.md` (gameplay events: what is collected and never collected), `docs/DPIA.md` (data protection impact assessment).
- **Team:** the main session builds everything; QA is an independent DeepSeek agent (`tools/qa.js`) in two CI jobs: `qa` (stage 1, required) answers closed questions YES or NO at low effort, each 3 times (the majority counts), and `qa-review` (stage 2) is the open review, advisory; before a promotion (the pull request from `dev` into `main`, which is production) every `qa-review` finding is fixed or answered. **Every pull request into `dev` carries a `## QA checks` section** written by its builder: one line per thing the change could break, `- [changes] file[, file]: question?` (YES on the new code, not YES on the old; at least one) or `- [stays] file[, file]: question?` (YES on the new code), phrased so YES means right, about behaviour, never "does X appear". A bug fix also adds its check to `test/past-failures.md`, which stage 1 asks again whenever a change touches its files. CI runs `tools/qa.js` from the base branch, and stage 1 reads `test/past-failures.md` from it: a change to either counts from the next pull request. The `ic-bug-fixer` and `ic-qa` agents are paused by the owner (QA runs in CI since #61).
- **Test plan:** the builder owns the test plan (each pull request's `## QA checks` and `test/past-failures.md`) and keeps improving it. A good check asks one fact, about behaviour, phrased so YES means right; says where ("sent to Sentry", not "sent"); is `[changes]` only if this change makes it true (what was already true is `[stays]`); names the files that hold the answer (the model cannot see library defaults); is answered by code, not comments (comments are not evidence). When a check misbehaves (a 2-1 vote, a wrong FAIL, a bug that got through), rewrite the question or add a past failure, and add the lesson here.
- **"continue"** from the owner means one turn of the team loop (triage, spec, build, pull request, verify, report; [docs/TEAM.md](docs/TEAM.md)): use the `team-loop` skill.
- **Branches:** `issue/<n>-<slug>` for one issue's work; `fix/`, `feat/`, `infra/` or `docs/` plus a short slug for work without its own issue. Into `dev` only by pull request: right after opening it, arm auto-merge with `sh tools/automerge.sh <n>` (it refuses any base but `dev`; the project's Claude Code settings allow it without asking). GitHub merges once `test`, `game` and `qa` pass; the branch need not be up to date with `dev`, because CI re-runs on `dev` after every merge. Render deploys every commit on `dev` and `main`; CI's `deployed` job proves it is live. A promotion into `main` (production) needs the owner's written go each time; then the owner, or on that go the main session, merges it. Agents never arm auto-merge on a pull request into `main`. GitHub does not enforce this.
- **Infrastructure:** everything is live production grade and dev mirrors production (owner, 2026-11-06). `render.yaml` is the only place a plan or service setting changes; Render applies it through its Blueprint (Render's sync of that file) `exs-dbndeu7f3r2c738bllag`. Never create a Free service or change settings in the dashboard. Details: `docs/OPERATIONS.md`.
- **Checks:** `npm test` (fast tests, then integration on the Docker stack); `npm run test:game` for game changes; `node tools/balance.js 10 <levels> none` for gameplay balance.
- **Diagrams:** always the `diagram-design` skill (https://github.com/cathrynlavery/diagram-design, MIT; Claude Code has it in `~/.claude/skills/diagram-design`, other agents install it with `npx skills add cathrynlavery/diagram-design`), default minimal light style. Never Mermaid (owner, 2026-11-07). Each diagram lives in `docs/diagrams/` as its HTML source plus a standalone SVG exported with `scripts/export_svg.py --system-fonts`; the markdown shows the SVG as an image. Redraw it in the same pull request that changes what it shows.
- **Text rules:** immune-system vocabulary on screen (no magic, armor, spell, tower); kid-level; honest biology, with an "In reality" note on every bend.
- `sed -i` is blocked in the agents' shell: edit with the Edit tool or a python heredoc that asserts each match.
